# Kubernetes

Kustomize manifests for the same services the compose stack runs (task 2.15). CI validates them without a cluster
(`validate.sh`: every build, then `kubeconform` in strict mode against Kubernetes 1.37); they are applied on a local
[kind](https://kind.sigs.k8s.io/) cluster by hand.

| Directory | What it holds |
|---|---|
| `base/` | The application tier: the investigator (Deployment, Service, HPA) and the three MCP servers. Probes, resource requests and limits, non-root pods with read-only root filesystems, network policies. No data stores and no secrets |
| `overlays/local/` | The whole stack for kind: the base, PostgreSQL (loaded with the seed by the compose init scripts) and a single-node Kafka, the replay adapter, the local-only passwords of the compose stack, and the repository's skills, fixtures and policy corpus mounted from the node |
| `monitoring/` | Two ServiceMonitors for the Prometheus Operator; applied apart, because they need its CRDs |
| `argocd/` | An optional Argo CD `Application` that keeps a cluster in step with the local overlay on `main` |
| `kind/` | `up.sh` creates the cluster and applies the overlay; `check.sh` checks what runs |

## Run it on kind

Needs Docker, [kind](https://kind.sigs.k8s.io/docs/user/quick-start/#installation) (checked with v0.33.0) and
`kubectl`, and the generated data (`cd data && uv run python generate.py`). Replay only: no key, no spend. About
3 GB of memory for the node.

```sh
bash deploy/k8s/kind/up.sh      # cluster, images (built by compose, loaded into the node), metrics-server, keys, apply
bash deploy/k8s/kind/check.sh   # see below
kubectl -n dispute-agent port-forward svc/investigator 8080   # the reviewer API on localhost:8080
kind delete cluster --name dispute-agent
```

`up.sh` reuses an existing cluster and keeps its approval keys, so it can be run again after a change. To reload the
seed after regenerating the data, delete the database's volume: `kubectl -n dispute-agent delete deployment postgres
&& kubectl -n dispute-agent delete pvc postgres-data`, then `up.sh` again. On the first start the MCP servers and the
investigator restart a few times while PostgreSQL loads the seed; they are ready once it is.

`check.sh` checks that every deployment is available and the seed loaded; that the investigator signs with the key
pair and actions-mcp holds and accepts the public key only; that actions-mcp's MCP port and ledger-mcp's answer the
investigator and refuse another pod, while their actuator ports stay open; that the reviewer API answers 401 without
its key; that the HPA reads CPU; and it runs one golden dispute (DSP-000018) through Kafka to its decision and
approves it, so a signed token crosses the network policy and actions-mcp records the write.

## How it differs from compose

- **Secrets.** The base references secrets and creates none. `dispute-agent-db` (each service's database password)
  and `reviewer` (the reviewer API key) are generated by the local overlay from the compose stack's local-only
  values. The approval keys (ADR 0005) are made per cluster by `up.sh` with the compose stack's generator and never
  touch the repository: `approval-signing` (private and public key, mounted into the investigator only) and
  `approval-verify` (the public key alone, mounted into actions-mcp). A live run needs the secret `anthropic`, which
  the investigator reads if it exists: `kubectl -n dispute-agent create secret generic anthropic
  --from-literal=api-key=...` (read the key from `.env` without printing it), then set `LLM_ADAPTER` in
  `investigator-config` to `anthropic`. A live run costs money.
- **Network policies.** actions-mcp (the only writer) and ledger-mcp answer the investigator only. Their actuator
  moved to a port of its own (9080, `MANAGEMENT_SERVER_PORT`) so probes and scrapes stay open while the MCP port is
  closed; policy-mcp serves public policy text and its metrics on one port and has no policy. kind's default network
  plugin enforces them; `check.sh` proves it.
- **Probes.** The Spring services use `/actuator/health/liveness` and `/readiness` on the management port with a
  five-minute startup probe; policy-mcp uses `/health`, which answers once the corpus is ingested.
- **Scaling.** The HPA scales the investigator on CPU from one to three replicas: the dispute topics have three
  partitions, so a fourth consumer would sit idle, and scale-down waits five minutes because a rebalance pauses the
  group. policy-mcp ingests the corpus at start-up, so it runs as one replica with the `Recreate` strategy.
- **Resources.** Requests are a little above what the pods use at rest on kind (investigator about 300 MiB,
  policy-mcp 390 MiB with its embedding model, the other servers about 180 MiB); limits leave room for a load run.
  The JVMs size their heap at 75% of the limit.
- **Observability.** Traces are off (`OTEL_TRACES_EXPORT=false`): the local overlay has no Tempo. The compose stack
  remains the place for the dashboard and traces; `monitoring/` wires the metrics into a cluster that runs the
  Prometheus Operator.

## Release images

The base names the images that compose builds (`dispute-agent/<image>:dev`). A version tag publishes the same four
to GitHub Container Registry (`.github/workflows/release.yml`) as `ghcr.io/<owner>/dispute-agent-<image>`; an overlay
for a real cluster points the base at them with Kustomize's `images` field:

```yaml
images:
  - name: dispute-agent/investigator
    newName: ghcr.io/<owner>/dispute-agent-investigator
    newTag: 0.1.0
  # likewise ledger-mcp, policy-mcp, actions-mcp
```

Pinned outside Dependabot's reach, bumped by hand: the kind node image (`kind/up.sh`, by digest), metrics-server
(`kind/up.sh`) and kubeconform (`.github/workflows/ci.yml`, with its checksum). The PostgreSQL and Kafka images
follow the compose stack's pins, which Dependabot bumps; `validate.sh` fails when the two differ.
