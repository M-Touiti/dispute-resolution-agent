# ADR 0001: Scope and the LLM provider port

- Status: accepted
- Date: 2026-11-01
- Deciders: repository owner

## Context

The repository must show, to a reader with eight minutes, that its author has built an agent that uses tools
through the Model Context Protocol, that cannot move money without a human, and that is evaluated and operated
like a production service. It must do so on synthetic data, with one API key, and without any artefact derived
from an employer.

Two scope questions have to be settled before the first line of code, because they shape every module:

1. What the agent does and does not do (so the evaluation has a fixed target).
2. How the model is reached (so fixtures, replay in CI, cost accounting and a future provider change are all
   possible without touching the agent loop).

Model ids and API behaviour change during a three-month build. On 1 November 2026 the investigator model is
`claude-opus-5-5` and the triage model is `claude-haiku-5-5`; the Anthropic Java SDK is at 3.3.0 (API version
2026-10-21). Any of these may change before the tag.

## Decision

### Scope

**In scope.** Cardholder disputes on single-currency card transactions in five reason categories (unauthorised
transaction, duplicate charge, goods not received, cancelled recurring, amount mismatch) plus two adversarial
evaluation categories (prompt injection in merchant data; cases that tempt an over-generous credit). The agent
investigates through three MCP servers, produces a validated structured decision (approve provisional credit,
request merchant evidence, decline, escalate), and may act only through an approval gate.

**Out of scope, stated in the README.** Real network reason codes, real chargeback submission, PCI data,
multi-currency, fraud models (the data carries a fraud flag; the agent reads it, it does not compute it), any
reuse of employer material.

**Data.** Entirely synthetic, generated by a seeded script in `data/`; the policy corpus is self-written plain
English modelled on the public structure of card-network dispute rules without copying any text or code.

### The LLM provider port

The application layer defines an `LlmPort` with one operation: send a conversation (system blocks, messages, tool
definitions, output configuration) and receive a response (stop reason, content blocks, usage including cache
read and cache creation tokens, the model that answered). The agent loop depends only on this port.

Three adapters implement it:

| Adapter | Purpose |
|---|---|
| `AnthropicAdapter` | Production path, Anthropic Java SDK pinned at 3.3.0 |
| `RecordingAdapter` | Wraps `AnthropicAdapter`; writes every request and response to `evals/fixtures/` keyed by a hash of the canonicalised request |
| `ReplayAdapter` | Serves recorded fixtures; the only adapter used in pull-request CI and in the k6 load test; a cache miss is a test failure, never a live call |

Rules that follow from the port:

1. **Model ids, effort and `max_tokens` live in configuration** (`application.yml`, environment variables),
   never in code. The audit log records the configured id and the id that actually answered (server-side
   fallbacks may differ).
2. **Cost is computed in the adapter** from a versioned price table in configuration keyed by model id; the
   price table version is recorded on every audit row and span.
3. **Re-baseline rule.** Any change to a model id, effort, the price table, the system prompt, a tool schema or
   the SDK major version must, in the same pull request: re-record the fixtures, re-run the deterministic suite,
   and (before a tag) re-run the full live evaluation and commit the regenerated `evals/REPORT.md`. A fixture
   cache miss in CI is the enforcement mechanism.
4. **The port is provider-neutral by shape, Claude-first in practice.** No second provider adapter is planned;
   the port exists for the recording and replay adapters and to keep SDK types out of the domain.

## Consequences

- The agent loop, the guard and the evaluation runner are testable without an API key.
- A model change is a configuration change plus a re-baseline, which is auditable in git.
- The adapter is the single place that knows the SDK's request shape (adaptive thinking by default, no
  `budget_tokens`, `output_config.effort`, `strict` tool definitions, structured output format, cache
  breakpoint on the system block, non-streaming). API rule changes touch one class.
- The recording adapter must canonicalise requests (sorted tool list, no timestamps) or the fixture key will
  drift; the same discipline keeps the prompt cache warm, so the two concerns reinforce each other.
- Cost: the port adds one indirection and one mapping layer between SDK types and domain types. Accepted.

## Alternatives considered

- **Call the SDK directly from the loop.** Simpler, but CI would need a key or a mock of SDK types, and a
  provider or SDK change would touch the loop.
- **Spring AI `ChatModel` abstraction.** Would give a port for free, but hides the Messages API features the
  project needs to show (cache control, effort, strict tools, structured outputs) behind a generic interface,
  and ties the MCP client to Spring AI as well. Rejected for the same reason as using Spring AI for MCP.
- **Second provider adapter from day one.** No reader asked for it; it would dilute the evaluation. Deferred.
